# RG-03 — Dispositivos autorizados y revocación

**Inicio:** 11/11/2026. **Estado:** P01 en desarrollo aislado, sin Release.
**Base:** `main` tras RG-02, commit `fb79509c42e0a36715943b3a7b5c1c2db1d72389`.

## Objetivo

Enumerar las instalaciones autorizadas de RobGuard y permitir revocar el acceso a la nube y solicitar el borrado local al dispositivo revocado cuando vuelva a conectarse. Dispositivos objetivo: Realme GT Neo 2 y Galaxy Tab S9+, aunque la tablet NO está disponible durante el desarrollo inicial. La prueba física conjunta pertenece a RG-04; RG-03 debe cubrir múltiples instalaciones con tests simulados y CI.

## Restricción crítica del modelo RG-02

RG-02 usa un solo Firebase Auth UID propietario para móvil y tablet. Las reglas actuales de Firestore conceden acceso a `/vaults/{ownerUid}` a **cualquier sesión con ese mismo UID**. Un registro de dispositivos solo en la interfaz NO puede revocar de forma efectiva una instalación. Borrar la sesión de Firebase o marcar un documento como revocado en cliente tampoco impide a un cliente antiguo, modificado u offline seguir utilizando su sesión mientras el servidor lo admita.

**Criterio innegociable para P02/P03:** autorización independiente por dispositivo, verificable por el servidor para CADA lectura/escritura de bóveda. No mantener las reglas RG-02 por UID propietario como vía alternativa de lectura de secretos después del cambio. La comprobación solo en la app no es suficiente. Fail-closed ante revocación, documento ausente o comprobación indeterminada. El dispositivo bloqueado no puede reactivarse usando su credencial revocada.

La infraestructura probable es un intermediario de confianza (p. ej., Firebase Cloud Functions, con su requisito de despliegue/facturación) que verifique identidad del propietario, inscripción de dispositivos y credenciales no reutilizables por otros equipos; el cliente no expondrá Firestore directamente con el UID propietario. Antes de elegirlo y desplegarlo se debe comprobar si el plan Firebase habilita Functions y documentar su coste. Si se estudia otro mecanismo, demostrar con pruebas que las reglas del servidor distinguen instalaciones: App Check genérico y un ID de dispositivo declarado por el propio cliente no lo consiguen.

## Subfases y criterios de aceptación

### RG-03-P01 — Identidad e inventario (sin cambios de seguridad en producción)

- Modelo tipado de estados y transiciones: PENDIENTE, AUTORIZADO, REVOCACIÓN_PENDIENTE, REVOCADO y BORRADO_CONFIRMADO.
- Identidad de instalación aleatoria, persistente, independiente de correo, Firebase UID y hardware ID. Clave privada específica de instalación en Android Keystore, nunca exportada; rotación/reinstalación requiere nueva autorización.
- Metadatos mínimos no secretos: alias editable, tipo/modelo general, fecha de alta, última comprobación confirmada por servidor y estado, sin geolocalización.
- Separar IDs generados por el cliente de autoridad: el registro no concede acceso por sí solo.
- Tests de máquina de estados, validaciones y casos anómalos. No mostrar datos de muestra como dispositivos reales.

### RG-03-P02 — Autorización y revocación efectiva en servidor

- Definir e implementar la frontera de confianza y la identidad independiente de cada instalación. Probar que dos dispositivos con el mismo Google UID NO comparten autorización de bóveda.
- Incorporar políticas de alta: aprobación desde un dispositivo activo o recuperación con Google + posesión del código de RG-02 mediante prueba criptográfica que **no transmita** el código al servidor, sin dar un mecanismo de reingreso automático a un dispositivo revocado.
- Reglas de Firestore y/o pasarela: denegar acceso directo a la bóveda a cualquier credencial que el servidor no haya reconocido como activa. Compatibilidad de esquema existente y migración atómica, sin dejar temporalmente una ventana de acceso demasiado amplia.
- Revocación autenticada con confirmación explícita y transacción resistente a carreras. No permitir borrar accidentalmente el último dispositivo de manera irreversible sin disponer de recuperación.
- Probar con cliente adversarial (peticiones directas a Firestore), no solo con botones de la UI: autorización inicial, escritura, lectura, revocación, tokens antiguos, reconexión y doble revocación.

### RG-03-P03 — Revocación y borrado local diferido

- Al recibir orden de borrado autenticada, bloquear acceso a la bóveda y eliminar archivos cifrados de bóveda, cache y baseline, además de los alias de Android Keystore correspondientes; registrar acuse sin recuperar secretos. Reintentos idempotentes y tolerantes a interrupciones.
- Prohibido borrar datos de otra instalación o la copia cifrada de Firebase por una revocación individual.
- Comprobación al inicio y antes de sincronizar, más comprobaciones cuando se recupere la conexión. Sin exigir actividad continua en segundo plano.
- **Límite real:** ninguna app corriente garantiza borrar datos si el dispositivo sigue offline, se ha manipulado, está apagado, desinstalado o no ejecuta RobGuard. Mientras no reciba la orden, la copia local puede seguir abriéndose; se recomienda bloqueo/borrado con las herramientas del sistema del propietario.

### RG-03-P04 — UI y pruebas de integración

- Pantalla «Mis dispositivos» en Ajustes: este dispositivo, restantes autorizados, última conexión **confirmada**, estado y controles con doble confirmación para revocar/borrar.
- Indicar claramente «orden pendiente» versus «borrado confirmado» y nunca mostrar «borrado» solo por registrar la petición.
- Tests automatizados de autorización/denegación, caducidad de credenciales, offline, recuperación, dos instalaciones, migración desde RG-02 y compatibilidad de datos.
- Android Lint, test Release, ensamblado Release sin firma y contrato RS-05 en verde.
- No entregar APK Debug; no tocar package ID `es.robertodorado.robguard`, certificado, versionCode de publicación ni secretos.
- Pruebas físicas en Realme GT Neo 2 y Samsung Galaxy Tab S9+ exclusivamente en RG-04 mediante RobPublisher → RS-05 → GitHub Release → RobStore.

## Condiciones de salida de RG-03

**NO fusionar** cambios que presenten una revocación como seguridad real mientras la ruta antigua de Firestore siga autorizando a cualquier sesión con el UID propietario. No publicar ni usar como almacén único hasta completar RG-04. No desplegar reglas que corten el acceso a la bóveda antes de que el cliente Release y el mecanismo de recuperación compatible estén listos.
